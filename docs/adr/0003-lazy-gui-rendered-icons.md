# Icons rendered lazily via GuiGraphics, not read from texture atlas

Icons are produced by rendering each `ItemStack` through `GuiGraphics.renderItem` into an offscreen framebuffer on Minecraft's render thread, at 2× GUI scale so each cell is 32×32 px; each filled sheet is encoded as one PNG and sent as an `Icon atlas` (ADR 0014). Rendering is lazy and budgeted — a small number of icons per frame, driven by the `IconBatch` stream — so no visible hitch is introduced even for heavy modpacks.

Reading sprites directly from the stitched texture atlas was rejected despite being much faster. The atlas is the pre-render input and does not represent: 3D block-item renders (chests, beds, banners), items with custom `BlockEntityWithoutLevelRenderer` (shields, tridents, bundles), model overrides (`pulling_bow`, `filled_bundle`), enchantment glint, or modded items with custom renderers. Covering all of these correctly requires the full GUI render path, matching what JEI, REI, and EMI all do.

Icons are rendered at 2× (32 px cells) rather than Minecraft's native 16 px because the app shows them at 32dp, around 80–96 device pixels on a phone, where 16 px 3D block items, glint and custom renderers looked visibly stair-stepped. Flat items gain no detail; their texels become 2×2 blocks. 4× was rejected for now: it would make decoded atlases take 16× the memory (about 128 MB for the app's default 256-atlas cache) and slow the read-back on the render thread. The app draws Icons with nearest-neighbour filtering at the largest whole multiple of 16 device pixels that fits the slot, so every texel is the same width on fractional screen densities.

An atlas fast-path for items whose model is a single flat texture with no overrides is a possible future optimisation if snapshot time becomes the bottleneck; it is deliberately not designed in now.
